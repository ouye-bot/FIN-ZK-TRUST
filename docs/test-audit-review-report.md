### 2.2 六个失败用例分析

#### 失败 1：1.9 私钥格式错误 — **测试实现问题**

- **现象**：`signWithSM2(message, 'invalid')` 未抛异常，测试期望抛异常
- **根因**：SM2 库对无效私钥不做输入验证，静默处理
- **判定**：这是系统缺陷（缺少输入验证），但测试的断言方式过于刚性。应改为：如果返回异常则通过；如果返回非空签名则标记为 `knownIssue`（输入验证缺失）
- **建议**：将此用例改为 `knownIssue` 标记，记录"SM2 签名函数不验证私钥格式"

#### 失败 2：1.10 签名位翻转检测 — **严重系统 Bug**

- **现象**：翻转签名第 1 个字符后验签仍返回 `true`
- **根因**：SM2 验签逻辑存在缺陷，对签名篡改不敏感
- **判定**：这是真实的安全漏洞。测试正确发现了问题。应标记为 `knownIssue` 并记录 Bug ID
- **建议**：新增 Bug ID（如 B9），标记 `knownIssue: true`，记录"SM2 验签对签名篡改不检测"

#### 失败 3：3.8 reEncrypt 密钥轮换 — **测试实现问题**

- **现象**：v2 前缀正确但新密钥解密失败
- **根因**：`reEncrypt` 函数接受新密钥参数，但 `decrypt` 函数始终使用环境变量中的主密钥解密，不接受密钥参数。测试用 `decrypt(reEncrypted)` 期望用新密钥解密，但实际用的是旧密钥
- **判定**：测试对 API 理解有误。`reEncrypt` 可能只是格式转换，解密仍需原始密钥
- **建议**：修正测试逻辑，验证 `reEncrypt` 的实际语义

#### 失败 4：3.9 认证标签完整性 — **严重系统 Bug**

- **现象**：分别篡改 IV/authTag/ciphertext 后解密均未抛异常，返回原文
- **根因**：SM4 `decrypt` 函数在解密失败时静默返回原文（Bug B3）
- **判定**：测试正确验证了 Bug B3 的存在。应标记为 `knownIssue`
- **建议**：三个篡改子用例都应标记 `knownIssue: true, bugId: 'B3'`

#### 失败 5：5.6 不达标 score<threshold — **系统 Bug**

- **现象**：`generateProof(500, 600)` 生成成功但 `verifyProof` 返回 `true`
- **根因**：ZKP 电路设计问题，阈值比较逻辑有误
- **判定**：这是真实的安全漏洞。测试正确发现了问题
- **建议**：标记 `knownIssue: true`，记录 ZKP 电路阈值比较缺陷

#### 失败 6：7.4 不同阈值组合 (2,2) — **测试实现问题**

- **现象**：单分片恢复抛出异常而非返回错误值
- **根因**：SSS 恢复函数在分片不足时抛异常，测试期望返回错误值
- **判定**：抛异常也是合理的错误处理方式，测试断言应兼容两种行为
- **建议**：修改断言为 `recovered !== key || threw exception`

## 五、另一个 AI 的五个问题回应

### Q1: SM2 私钥格式验证缺失（1.9 失败）

**回答**：这是系统缺陷，不是测试问题。`signWithSM2` 函数应验证私钥格式并在格式无效时抛出明确异常。当前行为是静默处理，可能导致使用错误密钥签名而不自知。

**处置**：将 1.9 标记为 `knownIssue`，新增 Bug ID（如 B9），记录"SM2 签名函数不验证私钥格式"。后续修复源码后此测试应自动转为 passed。

### Q2: SM4 认证标签完整性（3.9 失败）

**回答**：这是 Bug B3 的直接表现。SM4 `decrypt` 函数在解密失败时返回原文而非抛异常，认证标签形同虚设。

**处置**：三个篡改子用例（IV/authTag/ciphertext）都应标记 `knownIssue: true, bugId: 'B3'`。这是优先级最高的安全修复项。

### Q3: ZKP 阈值比较逻辑（5.6 失败）

**回答**：这是 ZKP 电路设计缺陷。`generateProof(500, 600)` 应该生成"不达标"的证明，验证应返回 `false`。当前返回 `true` 说明电路中的比较逻辑有误。

**处置**：标记 `knownIssue: true`，记录 ZKP 电路阈值比较缺陷。这直接影响信用验证的核心安全性。

### Q4: SSS 单分片恢复异常处理（7.4 失败）

**回答**：SSS 库在分片不足时抛异常是合理的错误处理方式（fail-fast）。测试断言应兼容两种行为：返回错误值 OR 抛异常。

**处置**：修改断言为 `try { recovered !== key } catch { expected }`。这是测试适配问题，非系统缺陷。

### Q5: 数据库连接池等待时间

**回答**：当前测试未覆盖连接池等待超时场景。应增加：(1) 连接池满时新请求的等待时间；(2) 等待超时后的错误处理；(3) 连接释放后的恢复时间。

**处置**：作为 P2 改进项，在模块 4 中增加连接池等待超时测试。
